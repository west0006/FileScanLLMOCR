# 开发中需要注意的点

---

## 一、架构层面的坑（致命级）

### ⚠️ 1. ARM 架构兼容性——第一个大坑

```
攀升坤龙一体机 = 鲲鹏 920S（aarch64 / ARM64）

不是 x86 服务器！以下全部受影响：
├── Docker 镜像：必须拉 aarch64 版本，x86 镜像直接报 exec format error
├── Python 包：C 扩展包（numpy/pandas/opencv）需要 ARM wheel
├── Elasticsearch：官方有 ARM 版本，但非官方插件（如 IK 分词器）需验证
├── PaddleOCR/PaddlePaddle：必须装 paddlepaddle-aarch64 + paddle-cann
├── MySQL：可用 MariaDB ARM 版或 MySQL 8.0 ARM 社区版
└── Node.js：ARM 版直接可用，但 native addon 需重新编译
```

**怎么做**：
- 第一天就用 ARM 虚拟机或云主机搭建开发环境，不要在 x86 Mac/PC 上开发完最后才适配
- CI/CD 中增加 ARM 构建流水线
- Dockerfile 中 `FROM --platform=linux/arm64`

### ⚠️ 2. 昇腾 NPU 不是 CUDA——第二个大坑

```
熟悉的东西                                 这个项目里的实际替代品
────────────────────────────────────────────────────────────────
nvidia-smi                         →    npu-smi info
CUDA / cuDNN                       →    CANN (Ascend 异构计算架构)
PyTorch (CUDA)                     →    torch-npu 或 MindSpore
GPU 推理                           →    NPU 推理，算子可能不兼容
vLLM / TGI                         →    MindIE 或 vLLM-ascend 分支
Flash Attention                    →    昇腾版实现（可能有性能差异）
```

**怎么做**：
- 提前在昇腾开发者社区确认所有依赖的算子支持情况
- PaddleOCR 的昇腾适配最成熟，优先走 PaddlePaddle 生态
- LLM 推理框架选型前先在真机上跑 benchmark
- 预留一个备选方案：如果昇腾推理性能不达标，是否降级为纯 CPU 推理（性能会大幅下降）

### ⚠️ 3. 单机部署的耦合风险

```
方案书：一台机器跑应用 + 数据库 + ES + AI 推理

风险：
├── ES 吃内存 + LLM 吃 NPU + OCR 吃 NPU = 资源争抢
├── Docker 隔离 ≠ 资源隔离，CPU/memory 超卖会相互影响
├── 如果 ES OOM，可能连带杀死 MySQL 容器
└── 运维噩梦：升级一个组件需要重启整机
```

**怎么做**：
- Docker Compose 中为每个服务设硬限制 `mem_limit` / `cpus`
- ES 堆内存不超过物理内存的 50%（`-Xmx16g` 如果 64GB 内存）
- LLM 推理进程用 cgroup 绑定 NPU 卡（推理独占一张卡、OCR 独占另一张）
- 监控到位：Prometheus + Grafana 起码覆盖 CPU/内存/NPU 使用率

## 二、前后端开发的坑

### ⚠️ 4. ES 索引设计不当 → 查不准

这个系统检索是核心功能，但很容易做烂：

```
❌ 错误做法：
  - 把所有字段 dump 进一个 index，用默认分词器
  - 不设字段权重，纯靠 BM25 默认分

✅ 正确做法：
  - 按 archive_id 路由分片（根据方案书按"归档年度"分片）
  - 字段映射明确：
      title:       text + ik_max_word + boost 3.0
      full_text:   text + ik_max_word + boost 1.0
      department:  keyword（精确匹配）
      year:        integer（范围查询）
      category:    keyword（聚合筛选）
      security_level: keyword
  - 同义词过滤器：学生→学籍, 毕业→校友, 成绩→成绩单
  - 自定义停用词（档案场景，"的""了""是"可以去掉）
```

### ⚠️ 5. OCR 文本直接入库的坑

```
❌ 错误做法：OCR 结果直接写入 ES 全文索引
  问题：
  - OCR 可能把 "档案" 识别成 "档桉"（繁简混用）
  - 印章覆盖区域的乱码 "囗囗囗" 会污染索引
  - 手写体识别错误率高，用户搜"张三"搜不到"张二"的档案
  
✅ 正确做法：
  1. OCR → 文本清洗管线：
     - 繁简统一（OpenCC）
     - 去除不可识别标记（囗/□/■）
     - 常见 OCR 错误纠正规则表
     - 段落合并去重
  2. 清洗后的文本 → ES 索引
  3. 保留原始 OCR 文本（用于对照浏览）
  4. 置信度 < 70% 的段落标记为 "低质量"，检索时降权
```

### ⚤ 6. 语义检索的延迟陷阱

```
方案书要求：语义检索 ≤ 5 秒
现实：32B LLM 推理一次可能就要 3-5 秒

问题：你不能让用户每次搜索都等 5 秒——太慢了

解法：
├── 方案 A（推荐）：异步两阶段
│   1. ES 关键词检索 → 200ms 返回初步结果
│   2. LLM 对 Top-20 结果做语义重排序 → 2-3 秒后台完成
│   3. 前端先展示初步结果，语义重排后增量更新
│
├── 方案 B：query 改写而非 document 理解
│   1. LLM 只解析用户 query（提取实体+意图）→ ~1 秒
│   2. 用解析结果构造 ES DSL → 200ms
│   3. 总延迟 ~1.5 秒
│
└── 方案 C：全量预计算（离线）
    对所有档案做 embedding → 向量数据库
    查询时只做向量相似度搜索 → < 500ms
    代价：embedding 模型需要单独训练或选择
```

**推荐**：方案 B（query 改写）用于语义检索主流程，方案 C 用于知识图谱关联推荐。

### ⚠️ 7. 前端原文浏览的性能坑

```
TIFF 文件：档案扫描常用格式，动辄 50-200MB/页
浏览器不支持原生 TIFF 预览！

✅ 做法：
  1. 后端实时转码：TIFF → PNG/JPEG → 前端
     风险：200MB TIFF 转码可能 5-10 秒
  2. 更好的做法：同步时预生成缩略图 + WebP 预览
     - 原始 TIFF 保留（下载用）
     - 预览用 2000px 宽的 WebP（~500KB/页）
  3. 前端用 OpenSeadragon 做深度缩放大图浏览
```

### ⚠️ 8. 批量操作超时

```
导出 1000 条检索结果 Excel → FastAPI 默认 30s 超时
导出 500 条档案原文压缩包 → 可能跑几分钟

✅ 做法：
  - 导出操作全部走 Celery 异步任务
  - 前端轮询任务状态 → 生成完成后提供下载链接
  - 下载链接设置有效期（如 24h），过期清理
```

## 三、AI 模型开发的坑

### ⚠️ 9. 32B 模型在昇腾 310P 上的真实性能

```
方案书声称：20 并发下 ≥10 tokens/s（INT8 量化）

实际情况需要验证：
├── 32B INT8 模型大小 ≈ 32GB，双卡 310P 各 24GB → 需要张量并行切分
├── 如果切分跨卡通信带宽不足，吞吐可能腰斩
├── 并发 10 时每请求平均速度可能远低于 10 tok/s
└── 批量审核任务场景：队列中可能有大量等待

✅ 必须做的：
  1. 拿到机器后立即做推理 benchmark：
     单请求延迟 / 并发 2/5/10 的吞吐 / KV cache 占用
  2. 如果性能不达标：
     - 考虑换 Qwen3-14B 做审核（14B INT8 单卡即可）
     - 或者审核用 7B/14B 模型，语义检索用 32B 模型
     - 7B/14B 微调后审核效果不一定比 32B 差
```

### ⚠️ 10. 训练数据泄露 → 评估作弊

```
❌ 错误做法：
  用同样的档案训练和测试
  → 评估准确率 95%，上线后 70%

✅ 正确做法：
  1. 按档案年度分层划分：老档案(1970s)训练 + 新档案(1990s)验证
  2. 跨归口单位划分：某些归口单位的档案全放测试集
  3. 时间外推测试：用 1980 年之前的档案训练，1990 年之后的测试
     （因为档案写作风格、敏感词分布会随年代变化）
  4. 最低要求：训练/验证/测试 = 70%/15%/15%，按 year 分层抽样
```

### ⚠️ 11. 敏感词库的误报问题

```
400+ 个敏感词，单纯关键词匹配的误报率极高：

例子：
  "关于学生处分的决定" → 触发 "处分" → 标记敏感
  但如果这是已结案的、不涉及个人隐私的行政管理文件呢？

  "文革" 出现在 "文化大革命结束后..." → 触发敏感词
  但如果这是在客观描述历史背景而非敏感内容呢？

✅ 做法：
  规则引擎的定位是"快速初筛"而非"最终判定"
  规则 + LLM 的分工：
  - 规则引擎：召回（宁多勿漏）→ 只要命中任意敏感词就标记候选
  - LLM：精判（去伪存真）→ 判断上下文，决定是否真敏感
  - 风险评分：规则命中数给 40% 权重，LLM 评分给 60% 权重
```

### ⚠️ 12. LLM 幻觉在审核场景特别危险

```
审核场景的两种致命错误：

类型 A：假阴性（漏判）——最危险
  档案包含 "关于某某事件的处理意见"（涉密）
  LLM 判定："该档案为普通行政管理文件，建议开放"
  → 涉密档案被公开，安全事故

类型 B：假阳性（误判）
  档案内容为 "学习中央文件精神"
  LLM 判定："涉及上级文件，建议不开放"
  → 本可开放的档案被封存，档案利用率下降

✅ 做法：
  - 宁可假阳性，不能假阴性（安全优先）
  - LLM 输出中增加 confidence 字段
  - confidence < 0.7 + risk_level=低 → 标记"需人工复查"
  - 在 Prompt 中明确："不确定时标注不确定"
  - 敏感词命中 + LLM 判定不敏感 → 强制标记争议项
```

## 四、安全开发的坑

### ⚠️ 13. 这是等保系统，安全不是"加上就行"的

```
方案书明确：等保二级要求
必须从设计阶段嵌入安全：

设计阶段必做的事：
├── 威胁建模：STRIDE 分析每个 API
├── 数据流图：标注每个节点间的信任边界
├── 敏感数据清单：哪些字段需要 AES-256 加密
└── 审计点设计：哪些操作需要记录到不可篡改的日志表

开发阶段必做的事：
├── 参数化查询（防 SQL 注入）——但 FastAPI + SQLAlchemy 默认安全
├── JWT 签名验证不放行过期 Token
├── 文件上传白名单（TIFF/JPG/PDF/PNG，拒绝 exe/bat/sh）
├── API 限流（防暴力破解和恶意导出）
├── CORS 严格配置（禁止 * origin）
└── HTTP 安全头：CSP / X-Frame-Options / X-Content-Type-Options

测试阶段必做的事：
├── SAST：静态代码扫描（bandit for Python, eslint-plugin-security for Vue）
├── DAST：OWASP ZAP 扫描
└── 第三方渗透测试（方案书要求的，不是可选的）
```

### ⚠️ 14. 日志中不能出现敏感内容

```
❌ 错误做法：
  操作日志中记录用户检索的完整内容：
  "用户搜索了：张三 家庭出身 历史问题"
  → 日志本身成了泄密源

✅ 做法：
  - 检索关键词脱敏后记录（只记录"关键词检索，结果 15 条"）
  - 档案原文内容不写入操作日志
  - 日志表单独权限控制，仅管理员可访问
  - 日志定期归档，生产库只保留 3 个月热数据
```

## 五、数据处理的坑

### ⚠️ 15. 增量同步的幂等性

```
方案书：通过比对文件修改时间戳和哈希值做增量同步

❌ 容易出问题的地方：
  - 源文件被覆盖但时间戳不变（某些 FTP 工具的行为）
  - 时间戳精度问题（FAT32 是 2 秒精度）
  - 大文件哈希计算耗时

✅ 做法：
  - 双重校验：时间戳 + 文件大小 + MD5 前 1KB（快速比对）
  - 完整 MD5 只在时间戳或大小变化时才计算
  - 同步记录表设计：
      sync_log (file_path, source_mtime, source_size, 
                content_md5, sync_time, sync_status)
  - 每次同步先查 sync_log，只有 hash 真正变了才更新
```

### ⚠️ 16. 大档案文件的 OCR 处理

```
一盒案卷可能包含几十到几百页扫描件
单页 TIFF 可能 100-200MB

❌ 错误做法：
  - 直接把 200MB TIFF 送给 PaddleOCR
  - 内存 OOM，或者处理一页 30 秒

✅ 做法：
  - 预处理时降采样到 300 DPI（档案扫描通常在 300-600 DPI）
  - 对超大图像先分块再识别（PaddleOCR 的 det + rec 本身支持）
  - 单页超时 30 秒自动跳过，标记为"处理失败"
  - OCR 任务分批（每批 50 页），避免内存峰值
```

## 六、项目管理层面的坑

### ⚠️ 17. 数据标注是最容易被低估的工作

```
方案书的项目计划中，没有独立的"数据标注"阶段
实际上标注工作量和开发工作量相当

真实时间预算：
├── OCR 标注：600 页 × 15 框 × 2 分钟 = 300 小时 ≈ 38 人天
├── LLM 审核标注：500 条 × 30 分钟 = 250 小时 ≈ 31 人天
├── 标注规范编写 + 标注员培训 + 质量抽检 ≈ 10 人天
└── 合计 ≈ 80 人天

✅ 做法：
  - 第 1 周就启动标注，不要等到"开发完成"
  - 需求调研阶段（前 20 天）和档案馆确认：能否提供 1996 年审核表作为种子数据？
  - 标注和开发并行排期
  - 预留至少 2 人专职标注（或外包 + 1 人质检）
```

### ⚠️ 18. 120 天工期 + ARM + 昇腾 = 缓冲时间很紧

```
方案书：120 个日历天（约 4 个月）
技术栈：全部需要在 ARM + 昇腾环境下验证

风险：
- 某个依赖在 ARM 上不可用 → 找替代方案 → 耗 3-5 天
- 昇腾驱动/CANN 版本不兼容 → 找华为技术支持 → 耗 1-2 周
- LoRA 微调效果不达预期 → 调整训练策略 → 耗 2 周

✅ 做法：
  - 硬件到货时间必须在第 20 天之前（需求调研结束前）
  - 拿到硬件第一周：只做环境搭建和兼容性验证，不做业务开发
  - 预留 2 周缓冲给 ARM/昇腾适配问题
  - 功能优先级严格分级：79 项功能中，23 个检索和 13 个预审是 P0，其余可以降级
```

# 线上开发模式 —— 核心矛盾与解法

## 核心矛盾

```
你日常的开发环境                        目标运行环境
┌─────────────────────┐          ┌─────────────────────────┐
│ x86 MacBook / PC    │          │ 攀升坤龙液冷一体机        │
│ macOS / Windows     │   部署   │ ARM64 (aarch64)          │
│ CUDA (可选)          │ ──────→ │ 昇腾 310P × 2           │
│ Docker Desktop x86  │          │ Docker CE ARM            │
│ 随便装包、随便试     │          │ 内网隔离、数据不出校园     │
└─────────────────────┘          └─────────────────────────┘
```

**一句话总结：你在 x86 上写的代码，最终要跑在 ARM + 昇腾上。而且目标机器在学校内网，你不能随时 SSH 进去调试。**

---

## 一、环境分层策略 —— 最关键的设计

你需要三层环境，而不是直接在自己的电脑上写完了扔过去：

```
┌─────────────────────────────────────────────────────────────────┐
│                       三层开发环境                                │
├──────────────┬──────────────────┬───────────────────────────────┤
│  L1 本地开发  │  L2 远程开发机    │  L3 目标验证机                  │
│  你的笔记本   │  云主机/内网x86   │  攀升坤龙一体机                 │
├──────────────┼──────────────────┼───────────────────────────────┤
│ x86          │ x86              │ ARM64 + 昇腾                   │
│ 写代码+单元测 │ CI/CD + 集成测试  │ 模型推理 + 性能测试 + 验收      │
│ Docker 本地跑  │ 模拟部署结构      │ 真机验证                       │
│ Mock 昇腾 API │ 全功能联调        │ 最终部署                       │
├──────────────┼──────────────────┼───────────────────────────────┤
│ 随便折腾      │ 提交后自动构建     │ 按计划预约使用                 │
│ 离线也能工作   │ 团队共享          │ 仅内网可访问                   │
└──────────────┴──────────────────┴───────────────────────────────┘
```

### L1：本地开发环境（你的 x86 笔记本）

```
能做的：
├── 前后端代码编写和调试（Vue.js / FastAPI）—— 这和架构无关
├── MySQL + ES + Redis + Celery 全部 Docker Compose 本地起
├── 单元测试、ES 查询语法调试、API 接口联调
├── OCR 和 LLM 调用的 mock 层——定义好接口，返回假数据
└── Git 提交、Code Review

不能做的：
├── 昇腾 NPU 相关的任何推理
├── ARM 原生编译的包验证
├── 真实 OCR/LLM 性能测试
└── 档案真实数据的处理（敏感数据不应出现在开发机）

Mock 层设计示例：
# app/services/llm_client.py
import os

class LLMClient:
    def __init__(self):
        self.mode = os.getenv("LLM_MODE", "mock")  # mock | real
    
    def review(self, text: str) -> dict:
        if self.mode == "mock":
            return self._mock_review(text)
        else:
            return self._real_review(text)
    
    def _mock_review(self, text: str) -> dict:
        # 返回固定的假数据，用于前端联调和 API 测试
        return {
            "risk_score": 45,
            "risk_level": "中",
            "sensitive_items": [...],
            "suggestion": "建议人工重点关注",
            "reason": "[MOCK] 这是开发环境模拟结果",
            "confidence": 0.85
        }
```

## 二、线上协作的具体工作流

### 2.1 每日开发流程

```
早上：
  1. 从 GitLab 拉取最新代码
  2. docker compose up -d 启动本地 L1 环境（MySQL+ES+Redis+API+前端）
  3. 开发功能（mock 模式下前端和后端都能跑通）
  4. 本地单元测试通过后提交 MR

CI 自动做的事（每次 push）：
  1. 拉取代码 → 安装依赖 → 代码静态检查（lint/format/SAST）
  2. 单元测试 + API 集成测试（mock 模式）
  3. 前端构建检查
  4. Docker 镜像构建（x86 版）
  5. 自动部署到 L2 集成环境
  6. E2E 测试（Playwright/Cypress）

定期（每周 2-3 次）：
  1. 从 x86 代码仓库 → 在 L3 昇腾机上拉取
  2. 用 ARM Dockerfile 构建镜像
  3. 切换 LLM_MODE=real，跑真模型验证
  4. 记录 ARM 特定问题 → 回 L1 修复
```

### 2.2 Docker 多架构构建策略

这是一个线上协作的核心技术点：

```dockerfile
# Dockerfile —— 需要同时支持 x86 和 ARM

# 使用多阶段构建 + 构建参数
ARG TARGETARCH
FROM --platform=linux/${TARGETARCH} python:3.11-slim

# 根据架构安装不同依赖
ARG TARGETARCH
RUN if [ "$TARGETARCH" = "arm64" ]; then \
        pip install paddlepaddle-aarch64 torch-npu; \
    else \
        pip install paddlepaddle torch --index-url https://download.pytorch.org/whl/cpu; \
    fi

COPY requirements.txt .
RUN pip install -r requirements.txt

COPY .. .
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```yaml
# docker-compose.yml —— 线上 L2 环境（x86）
services:
  backend:
    build:
      context: .
      args:
        TARGETARCH: amd64
    environment:
      - LLM_MODE=mock
```

```yaml
# docker-compose.arm.yml —— L3 昇腾环境（ARM）

    build:
      context: .
      args:
        TARGETARCH: arm64

      - ASCEND_VISIBLE_DEVICES=0,1

      - /dev/davinci1:/dev/davinci1

```

### 2.3 档案数据的安全处理

```
线上开发的敏感数据困境：
├── 档案扫描件和全文是敏感数据，不能离开校园内网
├── 但你需要真实数据来训练和测试 AI 模型
└── 你在校外开发时不能接触这些数据

解法：数据分层 + 脱敏流水线

L3（内网）                  L2（云/远程）             L1（你的电脑）
┌──────────────┐          ┌──────────────┐         ┌──────────────┐
│ 原始档案数据   │ 脱敏脚本  │ 脱敏测试数据   │  导出   │ 开发测试数据   │
│ 敏感词400+    │ ──────→ │ 替换后文本     │ ─────→ │ mock 假数据   │
│ 真实审核结果   │  (仅L3上) │ 统计特征      │         │ 单元测试用例   │
│              │          │              │         │              │
│ 永不出校园    │          │ 可用于集成测试  │         │ 开发日常使用   │
└──────────────┘          └──────────────┘         └──────────────┘

脱敏脚本（在 L3 上运行，输出脱敏后数据到 L2）：
  - 人名 → "张某某"、"李某某"
  - 身份证号 → "420106********1234"
  - 具体单位 → "某单位"、"某部门"
  - 保持文本长度和结构特征不变（对 OCR 测试仍然有效）
  - 保持敏感词分布比例（对 LLM 审核测试仍然有效）
```

### 3.2 真机上推荐部署 code-server

```bash
# 在昇腾一体机上安装 code-server（浏览器版 VS Code）
# 这样你通过 HTTPS 就能在浏览器里远程开发，和本地 IDE 体验接近

# 安装
curl -fsSL https://code-server.dev/install.sh | sh

# 配置（绑定内网 IP + 密码）
cat > ~/.config/code-server/config.yaml << EOF
bind-addr: 0.0.0.0:8443
auth: password
password: your-strong-password
cert: false
EOF

# 启动
systemctl --user enable --now code-server

# 通过 Nginx 反代 + HTTPS（用学校证书）
# 访问：https://archive-dev.zuel.edu.cn:8443
```

这样你在校外通过 VPN 连接后，浏览器打开就能直接在昇腾机上写代码、跑测试、看日志，体验和本地开发差不多。

## 四、团队协作规范（线上开发的软坑）

### 4.1 Git 分支策略

```
main              ← 生产就绪，只从 release 合并
  ├── develop     ← 集成开发分支，日常合并目标
  │     ├── feat/search-frontend    ← 每人一个功能分支
  │     ├── feat/ocr-api
  │     ├── feat/review-backend
  │     └── feat/llm-finetune
  └── release/v1.0 ← 测试稳定后从 develop 切出
```

### 4.2 MR 通过标准（写进 GitLab CI）

```yaml
# .gitlab-ci.yml 中的检查项
stages:
  - lint
  - test
  - build
  - deploy-l2

lint:
  stage: lint
  script:
    - ruff check backend/        # Python 代码规范
    - eslint frontend/src/       # 前端代码规范
    - bandit -r backend/         # Python 安全扫描

test:
  stage: test
  script:
    - pytest --cov=backend --cov-report=term
    - coverage >= 80% 否则 MR 不能合并

build:
  stage: build
  script:
    - docker build -t registry.example.com/archive-backend:$CI_COMMIT_SHA .
    - docker push ...

deploy-l2:
  stage: deploy-l2
  script:
    - ssh l2-server "docker compose pull && docker compose up -d"
  only:
    - develop
```

### 4.3 接口先定，Mock 先行

```
├── 定义好请求/响应的 JSON Schema
└── 前端拿着 Schema 直接写 mock，后端同步开发

# FastAPI 自动生成文档
# 开发时访问 http://localhost:8000/docs 就是完整的 Swagger UI

```

## 六、总结：线上开发模式下的关键决策

| 决策点 | 推荐方案 | 原因 |
|--------|---------|------|
| 代码托管 | GitLab（自建或 SaaS） | CI/CD 集成好，团队成员熟悉 |
| CI/CD | GitLab CI + Docker Buildx 多架构构建 | 同时产出 x86 和 ARM 镜像 |
| L2 集成环境 | 一台 x86 云主机（8C16G） | 跑除 AI 推理外的全部服务 |
| L3 真机访问 | VPN + code-server | 浏览器开发，体验接近本地 |
| 数据库初始化 | SQL 脚本 + Python seed 脚本入 Git | 新成员一键搭建环境 |
| AI mock 层 | 接口抽象 + mock/fake 实现 | 99% 开发不依赖真机 |
| 档案数据 | L3 上跑脱敏脚本 → 脱敏数据用于 L2 | 敏感数据不出校园 |
| 前后端协作 | OpenAPI 文档先于代码 | 并行开发不阻塞 |
