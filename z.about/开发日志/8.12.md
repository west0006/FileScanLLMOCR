## 二、六个系统性根因（先修这些，能一次性消掉大半）

### 根因 1：开发模式权限全放行
`security.py` 的 `require_role` 和 `require_permission` 在 `APP_ENV == "development"` 时直接 `return user`，不校验角色。而默认配置就是 development。这直接导致：
- reviewer 直接访问 `/log` 列表/导出返回 200
- reviewer 读审计摘要/报告返回 200
- 非管理员访问在线用户、用户管理、角色权限无拦截

```python
# security.py require_role() 内
if settings.APP_ENV == "development":
    logger.warning(f"[DEV] 权限放行: user={user['username']} ...")
    return user   # ← 所有角色都放行
```

### 根因 2：哈希链在并发写入下必然分叉（审计完整性）
`log_middleware.py` 的 `_write_log_sync` 用**独立线程**异步写日志，每条日志读「当前最新一条的 `chain_hash`」作为 prev。但多线程并发时，两条日志可能读到同一个 prev，形成分叉。`/log/audit/chain-verify` 按 id 升序重算校验，分叉处即报 `tampered`。这就是「145 条中 23 条异常」的来源——不是真被篡改，是**链生成算法在并发下不成立**。修复方向：写入加锁串行化，或改用「行号/id 确定性」而非「最新一条」作为 prev。

### 根因 3：SQLite `create_all` 不会迁移已存在的表
`models.py` 有 `session_id`、`chain_hash` 等列，`database.py` 用 `Base.metadata.create_all`。对**已存在的 `archive_dev.db`**，`create_all` 不会 ALTER 加列。所以「数据库列无 session_id」——旧库永远没有新列。修复：加一次轻量迁移（ALTER TABLE ADD COLUMN IF NOT EXISTS），或删库重建。

### 根因 4：后端用 `return {"error": ...}` + HTTP 200，前端不检查
`ocr.py`、`user.py`、`sync.py` 大量接口在业务失败时返回 `{"error": "..."}` 但状态码是 200。前端 `handleCreateTask`/`doCreate` 等只 `await` 后直接 `ElMessage.success('已创建')`，不检查 `res.data.error`。后果：
- 同名 OCR 任务、同名用户、超长任务名，后端其实拦住了，前端却提示「成功」
- 后端 `max_length=50`、重复检查**都存在**，但用户看到的是假成功

### 根因 5：日志操作类型未覆盖完整审计语义
`log_middleware.py` 的 `_GET_PAGE_MAP` 缺 `/api/log/`、`/api/stats/`、`/api/user/roles` 等页面的友好映射，`_OP_DETAIL_MAP` 把 download/export 都归到 `search` 模块、无独立 `download`/`export` 类型。前端 `OperationLogs.vue` 又用 `typeLabel()` 直接展示原始 `operation_type`（search/admin/login），不做「登录/功能访问/功能操作」三分类。加上 `_extract_target_id` 只对少数 URL 正则生效，`target_id` 大多为空 → 审计六要素不完整。

### 根因 6：前端 sortBy / 年份树等交互状态未接入重新检索
`SearchHome.vue` 里 `sortBy` 是普通 `ref`，`watch` 只监听了 `[activeCat, yearFrom, yearTo, activeOpenStatus]`，**没监听 `sortBy`**。所以切换排序不触发 `doSearch()` → 排序「完全无变化」。这是真实 bug，且是「排序未生效」的直接原因。

## 已坐实的缺陷（有代码证据）

### 1. PDF 导出 500 的根因 = `fpdf` 未安装
`export_service.py` 的 `export_to_pdf` 第一行就是 `from fpdf import FPDF`，但 `requirements.txt` 的「文件处理」段只有 `python-magic / Pillow / openpyxl`，**没有 `fpdf`**。

```python
def export_to_pdf(title, rows, columns, output_dir="/tmp"):
    from fpdf import FPDF   # ← ImportError → 全局异常处理器 → HTTP 500
```

所以「点 PDF 导出失败」「format=pdf 仍返回/异常」的根因是**依赖缺失**，不是逻辑错误。修复只需在 `requirements.txt` 加 `fpdf2`（注意：`fpdf` 是 PyPI 上的老包，正确包名是 `fpdf2`，`pip install fpdf2` 后 `from fpdf import FPDF` 可用）。

### 2. 预审风险分布全 0 的根因 = `ReviewRecord.task_id` 从未被可靠写入
- `review.py` 的单件 `preview` 落库时**不写 `task_id`**：`ReviewRecord(archive_id=..., risk_score=...)` 无 task_id 字段
- `seed.py` 的 `_generate_seed_reviews` 生成的预审记录也**无 task_id**
- 前端 `ReviewTaskList.vue` 读 `t.risk_dist?.high/medium/low`，后端 `_task_risk_dist(db, task_id)` 按 `ReviewRecord.task_id == task_id` 过滤 → 永远查不到 → 0/0/0

批量路径 `review_tasks.process_review_task` 倒是写了 `task_id=task.id`，但开发环境 Celery 常不跑（或 Redis 不可用 eager 模式），任务记录根本没生成。修复：`preview` 补写 task_id（或接受「单件预审不属于任务」的语义，改用「按 archive_id 全量统计」），并让 `_task_risk_dist` 用中英文键统一。

### 3. 预审结果未归档的根因
`_sync_open_status()` 只在 `preview` 里调用；批量 `review_tasks.py` 生成记录后**不调用**它，所以批量预审后 `Archive.open_status` 不更新。

### 4. 日志导出忽略筛选的根因（签名错配）
前端 `OperationLogs.vue` `handleExport` 传平铺参数：
```js
logApi.export({ user_account, operation_type, date_from, date_to })
```
后端签名是 `export_logs(format: str = "excel", filters: dict = {})`。FastAPI 把不认识 `format`/`filters` 的字段丢弃 → `filters={}` 空 → **导出全部日志，无视日期/用户筛选**。修复：前端改成 `logApi.export({ format:'excel', filters:{...} })`，或后端改平铺参数。

### 5. 排序未生效
`SearchHome.vue` 的 `watch` 只监听 `[activeCat, yearFrom, yearTo, activeOpenStatus]`，**不含 `sortBy`**，且排序 `<select>` 的 `@change` 也没绑 `doSearch`。

### 6. 假成功（OCR 同名 / 用户同名 / 超长名）
后端 `ocr.py`、`user.py` 都返回 `{"error": "..."}` + HTTP 200，前端 `handleCreateTask`/`doCreate` 只 `await` 不检查 `res.data.error`，直接 `ElMessage.success`。后端校验其实生效，用户看到的是假成功。

## 更新的 P0/P1 结论

补读后，最高优先级修复项收敛为 **6 个纯代码缺陷**（都定位到具体位置了）：

| # | 缺陷 | 位置 | 修复量 |
|---|---|---|---|
| 1 | `fpdf` 缺失 → PDF 导出 500 | `requirements.txt` + `export_service.py` | 1 行依赖 + 包名核对 |
| 2 | 哈希链并发分叉 → 误报 tampered | `log_middleware.py` `_write_log_sync` | 加锁/改确定性 prev |
| 3 | 权限 dev 放行 | `security.py` `require_role`/`require_permission` | 加开关 |
| 4 | 日志导出签名错配 | `OperationLogs.vue` `handleExport` + `log.py` `export_logs` | 前端改传参 |
| 5 | `task_id` 未写入 → 风险分布全 0 | `review.py` `preview` + `seed.py` | 补 task_id 或改统计口径 |
| 6 | 批量预审不回写 open_status | `review_tasks.py` | 落库后调 `_sync_open_status` |

外加一个横切项：**前端统一检查 `res.data.error`**，能一次消掉 OCR 同名/用户同名/超长名等「假成功」类 bug。

这 7 处（6 + 横切）修复量小、风险低、且都是「数据/安全/核心功能」级别的硬伤。要不要我按这个顺序开始改？还是先只改其中某几个？
